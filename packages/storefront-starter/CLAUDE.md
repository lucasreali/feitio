# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A client store built from the Feitio storefront starter: React with server-side rendering on TanStack Start, TanStack Router (file routes in `src/routes/`) and TanStack Query. `src/routeTree.gen.ts` is generated by the router plugin; never edit it. Everything internal (identifiers, comments, docs, commits) is written in English.

## After copying the starter out of the Feitio monorepo

Inside the monorepo, some tooling comes from outside this folder. In a store's own repository:

- add `vitest` and `typescript` as dev dependencies (the monorepo installs them only at its root);
- replace `@feitio/config` (a workspace package): copy its `tsconfig.react.json` into the project and point `tsconfig.json` at it;
- add a formatter and linter configuration (the monorepo's Biome config does not come along).

## UI

- The `frontend-design` plugin is enabled in `.claude/settings.json`. When using it, keep this project's choices over the skill's defaults:
  - Components are built on Base UI (`@base-ui/react`) and live in `src/components/ui/`. No shadcn/ui and no other component library.
  - Styling is Tailwind CSS with colors and radius only from the theme variables in `src/styles.css` (`background`, `foreground`, `primary`, `primary-foreground`, `muted`, `muted-foreground`, `accent`, `border`, `destructive`, `radius`). Use theme classes such as `bg-primary`; Tailwind's default palette is disabled, so raw colors do not exist. Each client's design changes the variables, not the components.
  - Icons come from Phosphor (`@phosphor-icons/react`). No Lucide.
  - Combine classes with `cn()` (`src/lib/cn.ts`) and build variants with `cva`.

## Adopting libraries

Installing a new library is always the developer's decision. This applies to every agent and developer and overrides an agent's autonomy.

1. **Need.** Before proposing a library, check in this order whether the need is already met by:
   - the language and the platform (Node, the browser);
   - what the project already has installed, including TanStack Start, Router and Query;
   - a little code of our own, simple and testable.

   Propose a library only when none of these solves it well. Always use an established library, never our own code, for cryptography, password hashing, authentication protocols, payments and parsing complex formats. Never propose a library for the convenience of one function, or one that overlaps a library the project already uses.
2. **Choice.** Compare at least two alternatives, plus using no library, on:
   - maintenance: recent releases, answered issues, not abandoned or deprecated;
   - adoption and maintainer: widely used, maintained by a known organization or team;
   - stack fit: ES modules, bundled TypeScript types, the Node version in use;
   - this project: works with React, Vite and server-side rendering; Base UI stays the only component library; weigh the size shipped to the browser;
   - official ecosystem packages over community ports;
   - license: permissive (MIT, Apache, BSD, ISC); flag any other;
   - security: no open known vulnerability, few transitive dependencies, care with install scripts;
   - weight: final size and performance impact.

   Read the library's current docs instead of relying on memory: versions change.
3. **Ask first.** Before installing any new library, stop and present:
   - the need, and why the options in item 1 do not solve it;
   - the alternatives compared, on the criteria in item 2;
   - the recommendation, and what is lost by choosing it;
   - whether it is a production or development dependency.

   Install only after explicit approval. The same holds for replacing a library, removing one or bumping its major version. The only exception is the types package (`@types/...`) of an approved library.
4. **After approval.** If the library sets a convention (for example, "dates always with X"), add one line to this file.

## API

The API client is generated by Kubb from the Feitio API's OpenAPI spec: `pnpm api:generate` writes types, Zod schemas, a fetch client and TanStack Query hooks to `src/api/gen/` (gitignored; never edit it). The base URL comes from `VITE_API_URL`. Store routes of the API need the store's tenant in the `X-Tenant` header.

## Commands

- `pnpm dev`: the store on port 3003.
- `pnpm build`: client and server bundles, then type-check.
- `pnpm test`: all tests. One file: `pnpm test <path>`. One test: `pnpm test -t "<part of the name>"`.

## TDD

Every new piece of code is built test first.

1. Write a test that describes the behavior you want.
2. Run it and see it fail, for the reason you expect (not a typo or a missing import).
3. Write the least production code that makes it pass.
4. Refactor with the tests green.
5. Repeat for the next behavior.

Rules:

- No production code without a failing test that asks for it.
- A bug fix starts with a test that reproduces the bug.
- Tests check what the user sees and does (rendered text, roles, interactions), not implementation details.
- A test you never saw fail is not trusted: make it fail once, for example by breaking the code it covers.
- A task is done only when every test passes.
- Test with Testing Library. Never test code generated by Kubb.
- Tests live next to the code as `src/**/<name>.test.ts(x)` and run in jsdom (`vitest.config.ts`).
